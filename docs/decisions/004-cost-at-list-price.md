# ADR-004: The cost ledger reports transcript usage at list price, and says so

Date: 2026-08-20
Status: accepted

## Decision
`COST_CONTROL.md` reports the token usage recorded in this project's Claude
Code session transcripts, valued at the published Claude API list prices in
`data/model-pricing.json`. It is generated by `npm run cost` and regenerated
in full on every run — never edited by hand.

**What it claims.** For each API request the transcripts record, the cost of
that request at published list rates, attributed to the agent that made it
(the orchestrator, or a subagent by its type), the model it used, the month
it ran in, and the pipeline line of the branch it ran on. Requests are
counted once each: streaming writes several transcript lines per request and
repeats `usage` on all of them, so records are deduplicated by message id.
Because the file is a pure function of the transcripts on disk, any number in
it can be re-derived by rerunning the script.

**What it does not claim.**

- **It is not an invoice.** Sessions run under a Claude subscription are not
  billed per token at all; for those, the figure is what the work *would*
  have cost on the API. Negotiated discounts, credits, and partner-platform
  rates (Bedrock, Google Cloud) are not modelled.
- **It is not complete.** Only transcripts on this machine are visible. The
  scheduled `refresh-research` and `apply` runs call
  `anthropics/claude-code-action` with a real API key and leave no local
  transcript, so that spend — genuine API spend — is missing until recorded
  in `data/cost-ci-runs.json`. Sessions run on another machine are missing
  too.
- **It is not exact.** Where the data is ambiguous the estimate understates:
  cache writes from transcripts that report no TTL split are priced at the
  cheaper 5-minute rate, and a model absent from the pricing table is flagged
  rather than silently costed at zero. Workflow attribution is the branch a
  request ran on, which approximates a pipeline line rather than proving one.
- **It is not benchmark data.** It measures this repository's own factory,
  not the tools under comparison. It must never appear on the served pages,
  feed a score, or be cited as evidence about a benchmarked tool.

## Context
Rule 1 says no data point changes without a verifiable source. A cost figure
is a data point, and the obvious place to get one — "ask the model what it
cost" — has no source at all. The transcripts do: every assistant turn
carries a `usage` block with the exact token counts the API returned, and
subagents write their own transcripts, so per-agent attribution needs no
instrumentation.

That still leaves the question of what a number derived from those counts
means. It is not what Anthropic billed: this project's interactive sessions
run on a subscription, and the two GitHub Actions workflows that *are*
API-billed leave nothing on disk to read. Publishing a single figure labelled
"cost" would invite exactly the reading the data cannot support.

The alternative sources were worse. Console billing totals are real invoices
but carry no per-agent or per-workflow breakdown, which is the whole question
being asked. Instrumenting the agents themselves is not possible — they are
subprocesses of a harness this repository does not control.

Two defects found while building it are the reason this ADR is explicit about
precision rather than just about billing. Deduplication was not obvious:
counting raw transcript lines inflated the total roughly threefold. And the
run log's command column originally matched any transcript that *quoted* a
slash command, so it credited `/refresh` to a session that never ran it
(PR #36) — a confident false claim in a file whose only value is being
trustworthy.

## Consequences
- Rates in `data/model-pricing.json` carry a source URL and a `checked` date,
  and change like any other sourced data point.
- The disclaimers above live in the generated file itself, not only here. If
  the generator stops emitting them, that is a defect.
- The ledger is regenerated once per session by the `SessionEnd` hook in
  `.claude/settings.json`. A `Stop` hook that regenerated it every turn was
  removed: it produced regeneration-only commits faster than they could be
  reviewed, and a stale-on-arrival diff is not a record.
- Closing the CI gap — having `refresh.yml` and `apply.yml` append their own
  usage to `data/cost-ci-runs.json` — is separate work. Until it is done, the
  ledger understates total spend, and the file says so.
- When a cost question needs an authoritative answer (an invoice, a budget
  commitment), the Anthropic Console is the source. This file is for seeing
  which agent and which pipeline line the spend went to.

## Amendment (2026-08-25): the ledger may not shrink

"Regenerated in full on every run" holds only where the run can see the
history. It cannot in a Claude Code web or remote session: that container is
cloned fresh and holds one transcript — its own. The `SessionEnd` hook fires
`npm run cost` there like anywhere else, and the file is a pure function of
the transcripts on disk, so the regeneration is *correct by its own
definition* and still catastrophic: it republishes the whole cumulative
ledger as that single session.

This is not hypothetical. In one web session on 2026-08-25 it happened four
times, offering $1.57, $9.93, $24.20 and $33.59 in place of a $103.92 ledger
covering five sessions and 727 requests. Each time the working tree came back
dirty and the stop hook asked for the change to be committed and pushed.
Nothing but an agent noticing the numbers stood between that and a commit
destroying four sessions of history.

So the rule gains a bound: **a run may not publish a ledger reporting fewer
requests or fewer sessions than the committed file already holds.** On the
machine that does the work every run sees a superset of the last, so a
shrink is never an update — it is a machine that cannot see the history.
`scripts/cost.mjs` compares against the committed totals and exits non-zero
without writing; `COST_ALLOW_SHRINK=1` overrides it for the case where the
shrink is real, such as a deliberately pruned transcript cache.

The guard is a safety catch, not a coverage fix. It protects what is already
recorded; it does not make an ephemeral container able to see history, and
spend from a session whose transcript never reaches the ledger machine
remains missing exactly as the Coverage section says.

## Amendment (2026-09-03): the priced records are committed, per session

The shrink guard held, and that exposed the next problem. On 2026-09-02 the
six September CI runs were recorded in `data/cost-ci-runs.json` — committed
data, in the repository, $41.13 of genuine API spend — and `COST_CONTROL.md`
kept saying no CI spend was included. It could not be regenerated from the
session that added the data, because that container could not see the 727
August requests and the guard correctly refused. It could only be
regenerated on the one machine holding the August transcripts, and nothing
had run there since. A ledger that is "a pure function of the transcripts on
disk" is a function of *one disk*, and the factory no longer runs on one
disk: every interactive session since 2026-08-24 has been a Claude Code web
session, whose transcript dies with its container and never reaches that
machine at all. Those sessions were not late to the ledger; they were
structurally unreachable by it.

So the records themselves are committed. `npm run cost` now does two things:
it reads every transcript the current machine can see and merges the priced
requests into `data/cost-ledger/<session>.json`, one file per session, and
then it renders `COST_CONTROL.md` from that store plus `data/cost-ci-runs.json`.
The merge is a union keyed by request: a machine adds what it can see and
never removes what another machine committed, so a pruned cache or a partial
transcript cannot shrink a session. A session's records are written by the
machine that ran it — a laptop, a web container, wherever — and any checkout,
including one with no transcripts at all, regenerates the same file from
them. The rendered ledger is a function of the repository.

What the store holds is what the transcripts' `usage` blocks said: request
id, timestamp, model, agent, branch, session and token counts. No prompt or
response text. One record per line, sorted, so a diff reads as the requests
that were added.

The shrink guard stays, unchanged, and now has a second job: it refuses the
run that would seed an empty store from a machine that cannot see the
history — exactly the September situation — until the machine that does has
run `npm run cost` once. After that seeding, a web session's `SessionEnd`
hook adds that session's records and the regenerated ledger to the working
tree, and committing them is the right thing, not the catastrophe the first
amendment describes.

Consequences:
- The store and the ledger move together. A run that is refused writes
  neither; a run that succeeds writes both. A ledger ahead of or behind its
  store is a defect.
- `data/cost-ledger/` is generated data, regenerated in place, never edited
  by hand, and — like the ledger — never served, scored, or cited.
- Two sessions ending at once produce two independent session files and a
  conflicting `COST_CONTROL.md`. Resolve by taking either side and running
  `npm run cost` on any checkout; the store is the record, the markdown is a
  render of it.
- The Coverage gap narrows to what it actually is: runs that leave no
  transcript anywhere, which is the two GitHub Actions workflows. Sessions
  are missing only until the machine that ran them has run `npm run cost`
  once and committed.
